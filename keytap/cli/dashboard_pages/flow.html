How a test run works

DashboardHow a run works

1. The big picture: five layers, each one calls the next

Read it top to bottom. Each box starts the box below it and waits for its answer.

You (or a schedule)nightly.py for an unattended night, suite.py run for one suite, replay.py for one recording.
Supervisor (nightly only)Goes through the suites and their tests in the order of suite.json. Checks the phone and battery, retries failures, asks the local model for help, writes the morning report.
suite.py runRuns one test. Adds the setup tests it needs first, restarts the app before each test, logs in if the test asks for it.
Engine and replayerPlays the test's steps on the phone one by one: tap, type, check. Retries a failing step, and fails the test if it keeps failing.
Result filesEverything is written to disk. The dashboard reads those files. Its Run panel can also start a run, by launching the same scripts you would type in a terminal.

2. The life of one test in a nightly

This is what the supervisor does for every test, one at a time. It tries a failing test up to 3 times.

1Pre-checkDoes the test use something unsafe overnight (wipe data, grant permissions)? Only if the config allows it. Is the phone online and the battery above the limit?
2Setup needed?Some tests need data another test creates (for example an invitation). That setup test runs first, unless the supervisor knows the data from earlier tonight is still fresh. Then it is skipped, and the dashboard shows "reused".
3Run the attemptsuite.py plays the test. The dashboard shows the step it is on, live.
It passedGo to the next test. If it only passed after a retry, it is marked "passed after a retry".
It failedThe supervisor reads why: a check failed, a button was missing, the app crashed, the phone vanished.
4Recover, then try again Phone problem: wait 30 seconds. Screen problem: the local model looks at the screen and closes error dialogs. Anything else: restart the app. Then the test starts again from its first step. If it fails the same way twice, the supervisor stops trying.
5After the last failed attemptThe local model writes a short diagnosis of what it saw (for example "wrong screen"). It never changes a test by itself. Then the next test starts.
An ANR (the app froze for a moment) used to fail a run even when every step passed. Now it only shows as a warning. A real crash still fails the run.

3. The life of one step

A test is a list of steps. A step is one tap, one typed text or one check.

Look for the element on the screenWait for it up to the time recorded for that step plus 10 seconds, or up to a fixed time if the step sets one. Shown as "waiting for the element".
FoundDo the action (tap, type, check). Some taps repeat themselves if the screen did not change.
Not found, and the step is optionalSkip it. For example a popup that only appears sometimes.
Not found, and it is requiredRetry the step up to 2 more times. Shown as "step failed, retry 1 of 2". If it still fails, the test fails.

Step options you will see mentioned in the results:

OptionWhat it doesWhy it exists
optionalSkip the step if its element never shows upPopups that only appear sometimes
whenRun the step only if an element shows up in timeThe OTP screen appears for some logins only
when_elseWith when: also watch for the screen that means "skip". Whichever shows first decidesA skipped step costs about a second, not the full wait
unlessRun the step only if an element is not on screenRecovery steps that only matter when something is missing
expectTap, then tap again until the next screen appearsTaps that get dropped while the screen is moving
verifyAfter typing, check the text arrived, retype if notTyped text arrives short or empty on a busy phone

4. Retries happen at three levels

When the dashboard says "retry", it helps to know which one. Before every step retry, the replayer first closes any dialog from the suite's blockers list (one screen read, free), and only then, if model help is on, asks the model.

LevelWhat is repeatedHow many timesWhat it costs
Step retryOnly the one failing step2 extra triesSeconds
AttemptThe whole test, from its first step, after a recoveryUp to 3 attempts in totalThe whole test again (up to minutes)
Model helpBefore a step retry, if no known dialog is in the way and model help is on: the local model looks at the screen and may close what is covering the appAt most 2 calls per test, 3 actions each10 to 40 seconds per call. A test that passes only after this is shown as "Passed with help"
Setup againThe setup test that creates data (it logs in, creates groups, logs in again)On every later attempt of a test that needs itAbout 4 to 5 minutes and 3 new groups

The setup test, step by step

1Log in as Hardeep
2Create group a, invite Siddharth, restart the app
3Create group b, invite, restart the app
4Create group c, invite
5Log in as Siddharth
6Open the Groups tab, check the newest invitation is group c
Invitations only appear if each account's "Auto-join groups" privacy setting is OFF (Profile, Privacy settings). With it ON, people are added to the group directly and no card is ever created.
Every test run leaves real groups and pending invitations on the test accounts. They pile up, which can change what the card shows after a while. The dashboard's "Groups created" counter shows how many a run made.

The dashboard judges a test by that test's own run, not by the nightly's summary line. If the two disagree it says so on the row.

7. Words used on the dashboard

  • Test: a recording with checks. It passes or fails.
  • Flow: a reusable recording (log in, close popups) that tests call.
  • Suite: a folder of tests and flows for one feature, with its order and settings in suite.json.
  • Setup test / seed: a test whose job is to create data for later tests.
  • Needs: "run this other test before me".
  • Reuse: skip the setup test because its data from earlier tonight is still fresh.
  • Attempt: one try at a whole test by the nightly supervisor.
  • Recover: what the supervisor does between two attempts to put the phone back in a good state.
  • Triage: the local model's short diagnosis after a test has failed for good.
  • ANR: "app not responding", the app froze for a moment.
